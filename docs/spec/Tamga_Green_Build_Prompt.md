## Сам промпт (копировать всё, что ниже, целиком)

```
Ты — Senior Full-Stack Engineer / Tech Lead и строишь проект Tamga Green.

К этому сообщению приложено 9 документов и 2 готовых актива — это ПОЛНАЯ спецификация
проекта, результат 9 этапов проектирования (продукт → UX → дизайн → архитектура →
БД → AI → каталог → админка → SEO). Твоя задача — не спроектировать проект заново,
а РЕАЛИЗОВАТЬ его точно по этим документам.

ЖЁСТКИЕ ПРАВИЛА:
1. Не изобретай новую архитектуру, если она уже описана в Tamga_Green_System_Architecture.md —
   следуй стеку (Next.js App Router + React + Tailwind + Supabase) и структуре проекта из него.
2. Не проектируй заново схему БД — используй SQL DDL из Tamga_Green_Database_Design.md
   как есть, оформляя как версионируемые миграции в supabase/migrations.
3. Не придумывай свои цвета/шрифты/отступы/радиусы — только токены из
   Tamga_Green_Design_Tokens.md, перенеси их в tailwind.config.ts один в один.
4. Каждую страницу/компонент сверяй с соответствующим разделом Tamga_Green_UX_Bible.md
   (какие кнопки, какие состояния — loading/empty/error — обязательны) и
   Tamga_Green_Plant_Catalog.md / Tamga_Green_Admin_Panel.md для каталога и CMS.
5. RLS обязателен на каждой таблице без исключений (см. Database Design, раздел 7.4) —
   ни одна таблица не должна остаться без политики.
6. AI-функции подключай в порядке приоритета из AI Architecture (раздел 14 — MVP:
   AI-описания, AI-поиск, AI-калькуляторы; остальное — позже). AI НИКОГДА не публикует
   контент автоматически — только готовит черновик, публикация — действие человека.
7. SEO must-have до запуска — по разделу 10.2 SEO Strategy (URL-структура, базовые
   Schema.org, robots.txt, sitemap, generateMetadata, hreflang, Core Web Vitals на
   карточке товара и категории).
8. plants-catalog.json — используй как seed для таблицы plants при первом запуске
   локальной БД (supabase/seed.sql или скрипт на его основе). Это реальные данные
   реального питомника, не тестовые заглушки — сохраняй структуру названий как есть,
   парсинг в атрибуты делай по пайплайну из AI Architecture, раздел 6.
9. landscaping_calculator.html — рабочий готовый компонент, встрой его логику как
   отдельную публичную страницу /calculator (перенеси JS-логику в React-компонент
   клиентского острова, подключи к реальным данным из БД вместо захардкоженного
   JSON, остальное — включая формирование заявки в WhatsApp — оставь как есть).
10. Если документ не даёт прямого ответа на возникший по ходу разработки вопрос —
    не останавливайся и не жди уточнения: прими наиболее логичное решение в духе
    остальных документов, зафиксируй его одной строкой в TODO.md с пометкой
    "[решено самостоятельно]" и продолжай. Уточнение у человека — только если
    вопрос критичен для безопасности данных или необратим (например, схема оплаты).

ПОРЯДОК РАБОТЫ (не пропускать фазы, не забегать вперёд):

Phase 0 — План.
  Прочитай все 9 документов. Составь TODO.md с фазами ниже, разбитыми на конкретные
  задачи. Не пиши код на этом шаге.

Phase 1 — Каркас.
  Инициализируй Next.js + TypeScript + Tailwind (конфиг с токенами) + Supabase
  (локальный CLI). Примени все миграции из Database Design как есть. Проверь RLS
  политики. Настрой next-intl (минимум locale 'en' + одна локаль пилотной страны).
  Definition of done: `npm run build` проходит без ошибок на пустом каркасе.

Phase 2 — Аутентификация и онбординг.
  Регистрация по ролям (поставщик/покупатель), форма компании, загрузка документов
  верификации в Storage, экран статуса верификации. RLS проверен на реальных
  запросах из двух разных тестовых аккаунтов (один не должен видеть данные другого).

Phase 3 — Каталог.
  Категории, карточка товара, список/грид, фильтры (динамические по attributes),
  поиск (сначала обычный tsvector — AI-слой позже), сравнение растений. Заполни
  локальную БД данными из plants-catalog.json через AI-пайплайн описаний
  (раздел 6 AI Architecture) — как минимум для 20 позиций вручную проверь качество
  разбора перед тем, как гнать все 165.

Phase 4 — Корзина и заказы.
  Мультивендорная корзина, чекаут, статусы заказа, заявки (`requests`) для
  нестандартных объёмов — по разделу 11 Plant Catalog.

Phase 5 — CMS / админка поставщика.
  Добавление товара, инлайн-редактирование цен/остатков, загрузка фото с AI-проверкой,
  импорт Excel с предпросмотром "было/стало" (раздел 7 Admin Panel) — обязательно
  протестируй импорт на реальном формате из plants-catalog.json/исходного прайса.
  Аналитика — минимум "продажи за период" и "топ по спросу".

Phase 6 — AI MVP.
  AI-описания (уже частично использованы в Phase 3), AI-поиск (embedding-канал поверх
  tsvector), AI-калькуляторы (объём для проекта, экономия при опте). Остальные 7 AI-
  функций — заглушки/бэклог, не блокируют MVP.

Phase 7 — SEO.
  generateMetadata по шаблонам, JSON-LD (Product/BreadcrumbList/WebSite минимум),
  robots.txt, sitemap-индекс, hreflang. Прогони Lighthouse на карточке товара и
  странице категории — LCP/INP/CLS в целевых порогах из SEO Strategy, раздел 7.1.

Phase 8 — Калькулятор озеленения.
  Встрой landscaping_calculator.html как страницу /calculator согласно правилу 9 выше.

Phase 9 — Финальная проверка перед демо.
  - [ ] Все happy-path флоу из UX Bible (раздел 15, "Ключевые пользовательские
        сценарии") пройдены руками хотя бы один раз
  - [ ] Нет console-ошибок на ключевых страницах
  - [ ] typecheck и lint чистые
  - [ ] RLS проверен на попытке доступа к чужим данным
  - [ ] Деплоится на Vercel + Supabase без ручных правок

После каждой фазы — короткий отчёт: что сделано, что отклонилось от документов и
почему, что осталось в TODO.md. Не пытайся сделать все 9 фаз за один проход — это
многосессионная работа, двигайся фазами и жди подтверждения после каждой, если явно
не попросили иначе.
```

## Как этим пользоваться

1. Открой Claude Code (или другой агент с доступом к терминалу и файловой системе).
2. Прикрепи 9 документов + `plants-catalog.json` + `landscaping_calculator.html`.
3. Вставь блок промпта выше целиком первым сообщением.
4. Дай агенту пройти Phase 0 (план) и покажи план тебе на согласование, прежде чем он начнёт писать код — это самая частая точка расхождения ожиданий, дешевле поймать её на этапе плана.

**Важная честная оговорка как от тех.лида:** фраза «построй полностью работающий проект» в один проход не работает ни для одного маркетплейса такого масштаба — 9 документов описывают систему на месяцы разработки. Промпт выше специально построен фазами с явным definition of done на каждой, чтобы агент не пытался сделать всё сразу поверхностно, а доводил до рабочего состояния по частям. Если хочешь, можем прямо сейчас, в этом чате, начать с Phase 0–1 (план + каркас проекта) — я могу собрать структуру репозитория и первые миграции здесь же, без переноса в другой инструмент.
