## 1. Структура каталога

### 1.1 Дерево категорий

Каталог строится на self-referencing дереве `categories` (Этап 5): категория верхнего уровня → подкатегория → (опционально) под-подкатегория. Пример реальной структуры на основе состава вашего прайс-листа (Этап 6):

```
Растения
├── Хвойные
│   ├── Туи
│   ├── Можжевельники
│   ├── Ели и сосны
│   └── Тис
├── Лиственные кустарники
│   ├── Барбарис
│   ├── Гортензии
│   ├── Пузыреплодник
│   ├── Бересклет
│   └── Вейгела
├── Деревья
│   ├── Клёны
│   ├── Граб, бук
│   └── Гинкго, ива
├── Почвопокровные и лианы
└── Декоративные травы
Сопутствующие товары
├── Грунты и субстраты
├── Инструменты
└── Опоры, крепёж
Готовые решения (см. раздел 9)
```

### 1.2 Страница категории

| Блок | Назначение | Источник данных |
|---|---|---|
| Хлебные крошки | Навигация вверх по дереву | `categories.parent_id` |
| SEO-текст (сворачиваемый) | 150–300 слов о категории для органического трафика (Этап 4, раздел 15.3) | `translations` (entity_type='category') |
| Подкатегории (плитки) | Быстрый переход глубже | дочерние `categories` |
| Панель фильтров | См. раздел 4 | `attributes` по `category_id` |
| Панель сортировки | По популярности / цене / новизне / рейтингу поставщика | вычисляется на бэкенде |
| Сетка товаров | См. раздел 3 | `plants` + `availability` + `prices` |
| Блок «Готовые решения из этой категории» | Перелинковка с разделом 9 | `landscape_solutions` через `solution_plants` |

### 1.3 Навигация

Верхнее мега-меню (desktop) раскрывает 2 уровня дерева категорий одновременно с превью самых популярных товаров; на mobile — drill-down навигация по одному уровню за экран (соответствует паттернам адаптивности из Этапа 4, раздел 14.1).

## 2. Карточка растения (страница товара)

Полная детальная страница объединяет все данные из Database Design (Этап 5) в единый экран:

```
┌─────────────────────────────┬─────────────────────────────┐
│                               │  Название (ru) · латынь       │
│   Галерея фото                │  Поставщик + рейтинг + печать │
│   (plant_images)              │  верификации (Этап 3, Seal)   │
│                               │  ─────────────────────────    │
│   [AI-проверено ✓/⚠]          │  Цена по объёму (таблица)      │
│   (Этап 6, раздел 7)          │  Остаток + «обновлено N ч назад│
│                               │  Кнопка [В корзину] [Сравнить] │
│                               │  Кнопка [Запросить цену] —      │
│                               │  если объём вне стандартных     │
│                               │  ступеней (раздел 11)           │
└───────────────────────────────┴─────────────────────────────┘
│ Описание (сгенерировано AI + подтверждено поставщиком, Этап 6)│
├─────────────────────────────────────────────────────────────┤
│ Характеристики (аккордеон, из plant_attribute_values):        │
│  зона морозостойкости · освещение · высота/ширина взрослого    │
│  растения · тип листвы · объём контейнера · форма кроны        │
├─────────────────────────────────────────────────────────────┤
│ Совместимые растения (раздел 8)                                │
├─────────────────────────────────────────────────────────────┤
│ Входит в готовые решения (раздел 9, если применимо)            │
├─────────────────────────────────────────────────────────────┤
│ Похожие товары / Часто покупают вместе (раздел 7)               │
├─────────────────────────────────────────────────────────────┤
│ Отзывы о поставщике (reviews, Этап 4)                          │
└─────────────────────────────────────────────────────────────┘
```

**Мобильная адаптация:** галерея — свайп на всю ширину, блок цены/остатка и кнопка «В корзину» — sticky снизу экрана, всё остальное — раскрывающиеся аккордеоны (полностью соответствует UX Bible, Этап 2, раздел 7.3).

**Состояние «нет в наличии».** Как показал ваш прайс-лист (2 позиции из 165 помечены «нет в наличии»), это частый статус, а не исключение — карточка не скрывается из каталога (важно для SEO), кнопка «В корзину» заменяется на «Сообщить о поступлении» (создаёт `requests`, Этап 5, тип `plant_availability_alert`), а под названием — явный статус вместо тихого нуля в остатке.

## 3. Карточка в списке (грид каталога)

Компактная версия карточки товара из Design System (Этап 3, «tag-card» — карточка в стиле бирки питомника):

- Фото (1 обложка, `plant_images.is_cover = true`)
- Название + латынь (мелким шрифтом)
- Цена «от» (минимальная ступень из `prices`)
- Бейдж наличия (`В наличии` / `Мало осталось` / `Под заказ`)
- Бейдж верификации поставщика (печать, Этап 3)
- Иконка ★ «В избранное» и чекбокс «Сравнить» (виден при наведении на desktop, всегда виден на mobile)
- При отсутствии подтверждённого перевода на локаль пользователя — карточка показывает английское название с мелкой пометкой (см. Этап 4, раздел 11) вместо пустого поля

## 4. Фильтры

### 4.1 Источник фильтров

Набор доступных фильтров **динамический**, а не захардкоженный — берётся из `attributes` для текущей `category_id` (Этап 5) с флагом `is_filterable = true`. Это значит, что у категории «Хвойные» будет фильтр «форма кроны», а у категории «Грунты» его не будет и вместо него появится «объём упаковки, л» — без изменения кода при добавлении новой категории.

### 4.2 Обязательные сквозные фильтры (не зависят от категории)

| Фильтр | Логика |
|---|---|
| Наличие | `availability.quantity > 0` |
| Цена | диапазон по минимальной цене в `prices` |
| Регион поставщика | `companies.country` |
| Рейтинг поставщика | `companies.rating_avg ≥ X` |
| Верифицирован | `companies.verification_status = 'approved'` (включён по умолчанию, отключаемо) |

### 4.3 Поведение

Полностью соответствует UX Bible (Этап 2, раздел 7.2): применённые фильтры — чипы над сеткой, живой пересчёт счётчика результатов на desktop, кнопка «Показать N товаров» на mobile. **Дополнение для этого этапа:** счётчик результатов у каждого значения фильтра (например, «Можжевельник (32)») вычисляется агрегирующим запросом по текущему срезу — предотвращает выбор комбинации фильтров с нулевым результатом.

## 5. Поиск

Интерфейс — единая строка поиска в шапке (UX Bible, раздел 7.1), под капотом — пайплайн AI-поиска из Этапа 6 (раздел 4): полнотекстовый + embedding-канал с fusion результатов.

**Дополнительно для каталога:**
- **Автодополнение** показывает не просто текстовые подсказки, а мини-карточки товаров (фото + цена) после 2 символов ввода — сокращает путь до товара для точных запросов («туя брабант»).
- **«Возможно, вы имели в виду»** — при опечатке или нулевом результате поиск предлагает ближайшее совпадение по названию из каталога, а не просто сообщение об ошибке.
- **Поиск внутри отфильтрованной категории** — если пользователь уже находится на странице категории «Хвойные», поисковая строка по умолчанию ищет внутри неё, с явной опцией «искать по всему каталогу».
- **История и сохранённые запросы** — привязаны к `users.id`, доступны из личного кабинета покупателя (UX Bible, раздел 7.1).

## 6. Сравнение растений

### 6.1 Механика

- Чекбокс «Сравнить» на карточке (список и деталь) добавляет товар в сессионный список сравнения (до 4 позиций одновременно — больше не помещается читаемо ни на одном брейкпоинте).
- Плавающая панель внизу экрана показывает миниатюры выбранных товаров и кнопку «Сравнить (N)», доступна на любом экране каталога, пока список не пуст.
- Сравнение ограничено товарами **одной категории** (сравнивать тую с грунтом бессмысленно) — при попытке добавить товар другой категории интерфейс мягко предупреждает и предлагает начать новое сравнение.

### 6.2 Страница сравнения

Таблица: столбцы — выбранные товары (фото, название, цена, поставщик), строки — характеристики из `plant_attribute_values`, объединённые по `attribute_id` так, чтобы сравнивались только применимые к этой категории поля. Различающиеся значения подсвечиваются (например, разная зона морозостойкости выделяется цветом), совпадающие — остаются нейтральными, чтобы взгляд сразу цеплялся за реальные различия.

**Пример на реальных данных.** Сравнение «Можжевельник скальный Блю Эрроу» / «Можжевельник обыкновенный Хиберника» / «Можжевельник горизонтальный Глаука» из вашего прайса сразу показывает то, что не видно из одних названий: колонновидная форма против стелющейся — ключевой параметр выбора, который в сыром прайс-листе никак не выражен, а в структурированном сравнении — первая же строка таблицы.

### 6.3 Действия со страницы сравнения

Кнопки «В корзину» напротив каждого товара, «Экспорт в PDF» (раздел 10), «Поделиться сравнением» (публичная ссылка — полезно, когда закупщик согласовывает выбор с руководством внутри своей компании).

## 8. Совместимые растения

Новая для каталога сущность — компаньонная посадка (какие растения хорошо соседствуют, а какие подавляют друг друга по свету/влаге/корневой конкуренции). Требует небольшого расширения схемы БД (Этап 5):

```sql
create table plant_compatibility (
  id uuid primary key default gen_random_uuid(),
  plant_id_a uuid references plants(id) on delete cascade,
  plant_id_b uuid references plants(id) on delete cascade,
  relation text not null check (relation in ('companion','incompatible')),
  reason text,                      -- краткое пояснение ("конкурируют за влагу", "контрастная текстура")
  source text default 'expert',     -- 'expert' | 'ai_suggested' — прозрачность происхождения данных
  check (plant_id_a <> plant_id_b)
);
create unique index idx_plant_compat_pair on plant_compatibility(least(plant_id_a, plant_id_b), greatest(plant_id_a, plant_id_b));
```

**На карточке товара:** блок «Хорошо сочетается с» (relation='companion') — до 4 карточек-миниатюр с прямым переходом; отдельно, менее заметно — предупреждение «Не рекомендуется рядом с» для агротехнически конфликтующих видов, если такие данные есть.

**Источник данных:** первично заполняется агрономом/контент-командой (`source='expert'`), может быть предложено AI-дизайнером (Этап 6, раздел 5) на основе паттернов реальных `projects`/`solution_plants` — такие записи помечаются `source='ai_suggested'` и требуют подтверждения эксперта перед тем, как влиять на публичные рекомендации (тот же принцип human-in-the-loop, что и в AI-описаниях).

## 9. Готовые решения

### 9.1 Каталог решений

Отдельный раздел навигации (см. раздел 1.1) — сетка карточек `landscape_solutions` (Этап 5): фото, название, цена «от», краткое описание. Фильтруется по назначению (живая изгородь / клумба / контейнерное озеленение / кровля) через тот же механизм атрибутов, что и обычный каталог.

### 9.2 Страница решения

- Галерея (реальные фото из связанных `projects` через `project_solutions`, а не только студийные фото — реализованные объекты продают лучше абстрактной схемы)
- Состав решения — таблица `solution_plants`: растение, количество на единицу (например, «на погонный метр»), фото, ссылка на карточку
- Калькулятор («сколько метров изгороди — сколько растений нужно», Этап 2, раздел 9.2 / Этап 6, раздел 12) — встроен прямо в страницу решения, а не только в общий раздел калькуляторов
- Кнопка «Добавить решение в корзину целиком» — рассчитывает количество каждого растения по введённым метрам и добавляет всё одним действием, распределяя по поставщикам (мультивендорная логика корзины, Этап 2, раздел 8.1)

## 10. Экспорт в PDF

### 10.1 Что можно экспортировать

| Источник | Содержимое PDF |
|---|---|
| Карточка товара | Одностраничная спецификация — фото, характеристики, цена, поставщик, QR-код на страницу товара |
| Сравнение (раздел 6) | Таблица сравнения в брендированном оформлении |
| Корзина заявок | Коммерческое предложение — состав, цены, итог, реквизиты поставщика(ов) — готово для внутреннего согласования у покупателя |
| Каталог поставщика целиком | Полный прайс-лист в PDF — актуальная замена ручных Excel-прайсов вроде того, что вы прислали на Этапе 6 |

### 10.2 Техническая реализация

Генерация — на сервере (Supabase Edge Function `export-pdf`), не в браузере: HTML-шаблон на основе токенов Design System (Этап 3) рендерится headless-браузером (Puppeteer/Playwright) в PDF и отдаётся по подписанной временной ссылке, либо кладётся во временный Storage bucket `exports` с TTL 24 часа. Такой подход гарантирует, что PDF выглядит идентично на любом устройстве пользователя, а не зависит от локального рендеринга.

## 11. Формирование заявки

Заявка (`requests`, Этап 5) — более лёгкая по сравнению с полноценным заказом (`orders`, Этап 4) сущность, покрывающая три сценария, где оформление обычного заказа избыточно или невозможно:

### 11.1 Точки входа

| Где | Когда | Тип заявки |
|---|---|---|
| Карточка товара | Товар «нет в наличии» | `plant_availability_alert` |
| Карточка товара / сравнение | Нужен объём вне стандартных ценовых ступеней (например, оптовая закупка под проект тысячами штук) | `quote` |
| Страница готового решения | Нужна консультация перед покупкой большого проекта | `project_consultation` |
| Любая страница (футер/AI-помощник) | Общий вопрос платформе | `contact` |

### 11.2 Флоу заявки на цену (`quote`) — самый частый сценарий B2B

1. Покупатель на карточке товара нажимает «Запросить цену» вместо «В корзину» (эта кнопка появляется, когда введённое количество выходит за верхнюю границу таблицы `prices`).
2. Форма: желаемое количество, желаемая дата поставки, комментарий — минимум обязательных полей, остальное подтягивается автоматически (товар, покупатель, компания).
3. `requests` создаётся со статусом `new`, уведомление уходит и поставщику, и, если поставщик не ответил в SLA (например, 24 часа), — администратору платформы (перекликается с AI-помощником менеджеру, Этап 6, раздел 9).
4. Поставщик отвечает предложением цены прямо в переписке (`conversations`/`messages`, Этап 5) — при согласии покупатель одной кнопкой превращает заявку в обычный `order` с зафиксированной индивидуальной ценой (не через стандартный чекаут с прайсовыми ступенями).
5. Статус `requests.status` переходит в `closed`, `order_id` сохраняется как ссылка для истории.

### 11.3 Почему не просто «расширить корзину»

Нестандартный объём/цена требует человеческого подтверждения поставщика прежде, чем деньги спишутся — заявка explicitly отделяет «интерес и переговоры» от «подтверждённой сделки», что отражает реальный B2B-процесс закупки (PRD, Этап 1, journey покупателя) и защищает обе стороны от автоматического оформления заказа по цене, которую поставщик ещё не подтвердил.

## 12. Сводная модель данных каталога

```
categories ──1:N── plants ──1:N── plant_images
     │                │  │
     │ 1:N             │  ├─1:N── availability
     ▼                 │  ├─1:N── prices
attributes             │  ├─M:N (plant_attribute_values)── attributes
     │                 │  ├─M:N (plant_compatibility)── plants (self)
     └─1:N (per cat)   │  ├─M:N (solution_plants)── landscape_solutions
                       │  └─1:N (полиморфно, translations)
                       │
                       └── избранное (favorites) · сравнение (session/local) · заявки (requests)

landscape_solutions ──M:N (project_solutions)── projects ──1:N── gallery_images

requests ──N:1── users, ──полиморфно── plants / landscape_solutions
exports (PDF) — временная таблица/bucket, без постоянного хранения
```
