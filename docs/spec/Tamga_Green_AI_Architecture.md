## 1. AI как сквозной слой, а не отдельный модуль

Десять функций из этого этапа не десять разных систем — это десять точек входа в **один AI-слой**, построенный на Edge Functions из Этапа 4 (`ai-assistant`, `calculate-shipping` и др.) и таблицах `attributes`, `translations`, `ai_cache` из Этапа 5. У всех фич общий фундамент:

```
                      ┌─────────────────────────────┐
                      │       Данные платформы        │
                      │  plants · attributes · orders  │
                      │  translations · gallery · ...  │
                      └───────────────┬─────────────────┘
                                      │
                      ┌───────────────▼─────────────────┐
                      │      AI Orchestration Layer       │
                      │  (Supabase Edge Functions)         │
                      │  · маршрутизация запроса к нужной  │
                      │    модели/пайплайну                │
                      │  · сборка контекста (RAG)           │
                      │  · function calling к БД/калькулят. │
                      │  · кэш (ai_cache) и лимиты          │
                      └──┬─────────┬─────────┬─────────┬───┘
                         │         │         │         │
                 ┌───────▼─┐ ┌─────▼───┐ ┌───▼─────┐ ┌─▼──────────┐
                 │ Текстовая│ │ Vision   │ │ Embedding│ │ Модель      │
                 │ LLM      │ │ LLM      │ │ модель   │ │ перевода     │
                 │ (Claude) │ │ (Claude) │ │ (поиск)  │ │ (Claude/спец)│
                 └──────────┘ └──────────┘ └──────────┘ └─────────────┘
```

Каждая из 10 функций ниже описана как: **что делает → вход/выход → пайплайн → пример на реальных данных → где хранится → риски**.

## 2. Общая архитектура AI-слоя

### 2.1 Оркестрация

Единая Edge Function `ai-orchestrator` принимает запрос с обязательными полями `feature` (одно из 10 ниже), `role`, `company_id`, `locale`, `payload`. Внутри — простой роутер:

```
feature = 'plant_matching'      → pipeline: structured-filter + rerank (текстовая LLM)
feature = 'search'              → pipeline: embedding-поиск + fallback на pg_trgm (Этап 4, п.9)
feature = 'designer'            → pipeline: RAG(landscape_solutions) + генерация схемы раскладки
feature = 'description'         → pipeline: parse-raw-name → structured attrs → generate copy
feature = 'photo_check'         → pipeline: vision-модель → сравнение с заявленным видом
feature = 'translate'           → pipeline: перевод + terminology-guard (ботанический глоссарий)
feature = 'manager_assistant'   → pipeline: RAG(orders/requests) + function calling
feature = 'recommendations'     → pipeline: embedding similarity + collaborative signals
feature = 'solution_generator'  → pipeline: constraint solver + RAG(solution_plants) + LLM-компоновка
feature = 'calculator'          → pipeline: детерминированная формула + LLM только для интерпретации ввода
```

### 2.2 Принцип «LLM не считает — LLM понимает»

Ключевое архитектурное решение для всех 10 фич: **везде, где есть точная формула (объём, цена, количество саженцев), считает не LLM, а обычный код**. LLM отвечает только за то, что не формализуется — понять свободный текст запроса, сгенерировать описание, оценить визуальное сходство. Это радикально снижает риск галлюцинаций в местах, где ошибка стоит денег (например, расчёт количества растений на проект).

## 3. AI-подбор растений

**Что делает.** Пользователь описывает условия (климатическая зона, освещение, тип почвы, назначение — живая изгородь/одиночная посадка/контейнер) — AI возвращает ранжированный список подходящих растений из реального каталога поставщиков, а не из общей ботанической базы знаний.

**Вход:** структурированная форма (зона морозостойкости, освещённость, влажность, высота/ширина ограничения, бюджет) **или** свободный текст («нужно что-то вечнозелёное для тени под забором, зона 5»).

**Пайплайн:**
1. Свободный текст → LLM извлекает структурированные параметры (function calling: `{hardiness_zone, light, purpose, max_height}`).
2. Структурированный фильтр по `plants` + `plant_attribute_values` (Этап 5) — это **обычный SQL-запрос**, не LLM, чтобы гарантировать, что рекомендованное растение реально есть в наличии (`availability.quantity > 0`).
3. Из отфильтрованного набора (обычно 20–80 позиций) LLM делает финальный rerank по соответствию описанным условиям и пишет объяснение выбора для каждой позиции.

**Пример на реальных данных.** Запрос: «вечнозелёное растение для живой изгороди, зона 5, высота до 2 метров». Фильтр по `attributes` (`hardiness_zone ≤ 5`, `foliage_type = evergreen`, `category = hedge`) в вашем прайсе вернёт кандидатов из группы **Можжевельник** (32 позиции в прайсе — самая крупная товарная группа) и **Туя** (21 позиция) — AI объяснит разницу между, например, «Можжевельник скальный Блю Эрроу» (колонновидная форма, для акцентной посадки) и «Туя западная Брабант» (классика именно для плотной живой изгороди) вместо того, чтобы просто вывалить оба варианта без контекста.

**Где в БД:** читает `plants`, `plant_attribute_values`, `availability`; пишет сессию в `ai_chat_sessions`/`ai_chat_messages` (Этап 4).

**Риск и защита:** AI не должен утверждать морозостойкость или токсичность, если это поле пустое в `plant_attribute_values` — вместо выдумывания значения интерфейс показывает «данные уточняются» и создаёт `requests` (Этап 5) с типом на уточнение у поставщика.

## 4. AI-поиск

**Что делает.** Расширяет обычный поиск (Этап 4, раздел 9 — Postgres full-text) пониманием синонимов, опечаток, ботанических и бытовых названий, а также смешанных языков запроса.

**Пайплайн:**
1. Запрос идёт параллельно в два канала: (а) классический `tsvector`-поиск, (б) embedding-поиск по векторному индексу названий/описаний.
2. Результаты объединяются (reciprocal rank fusion), если embedding-канал находит семантически близкое, но лексически непохожее совпадение — например, запрос «туя для забора» находит товары без слова «забор» в названии, потому что оно есть в семантике «живая изгородь».
3. Для нового/неполного запроса (меньше 3 совпадений) — LLM предлагает переформулировку и синонимы, которые сохраняются в `search_synonyms` (Этап 4) для будущих запросов без повторного вызова модели.

**Пример на реальных данных.** Ваш прайс не содержит слова «можжевельник виргинский», зато есть «Можжевельник скальный». Покупатель, ищущий по бытовому названию или ошибившийся в виде, всё равно должен увидеть релевантные позиции — embedding-канал решает это без ручного составления тезауруса на 165+ позиций (а в будущем — на десятки тысяч).

**Где в БД:** индекс на `plants.search_vector` (Этап 5) + отдельная векторная таблица `plant_embeddings(plant_id, embedding)`; кэш популярных запросов — в `ai_cache`.

## 5. AI-дизайнер

**Что делает.** По параметрам участка (площадь, форма, освещение, стиль — регулярный/природный/минималистичный, бюджет) генерирует черновую схему озеленения: зонирование + подобранные растения из каталога + примерная смета.

**Пайплайн:**
1. Пользователь задаёт параметры через форму или загружает фото/план участка.
2. LLM с function calling обращается к «AI-подбору растений» (раздел 3) для каждой зоны схемы (передний план/фон/акценты) — дизайнер **переиспользует**, а не дублирует пайплайн подбора.
3. Генерируется текстовое описание раскладки + упрощённая 2D-схема (SVG, генерируется детерминированным кодом на основе структурированного плана от LLM, а не самой моделью — во избежание визуальных галлюцинаций) + список растений с количеством и итоговой ценой из `prices`.
4. Результат можно одним кликом превратить в заявку (`requests`, type=`project_consultation`) или сразу в корзину.

**Пример на реальных данных.** «Участок 6×20м вдоль забора, хочу многоярусную живую изгородь, бюджет средний» → AI-дизайнер предложит трёхъярусную схему: задний ряд — Туя западная Брабант Co10 140-160 (2400 ₽/шт, для высоты), средний — Пузыреплодник калинолистный Диаболо (900 ₽/шт, для цветового контраста бордовой листвой), передний — Барбарис Тунберга Багатель (1000 ₽/шт, компактный) — с расчётом количества через AI-калькулятор объёма (раздел 12) и итоговой суммой напрямую из вашего прайса.

**Где в БД:** результат сохраняется как черновой `project` (Этап 5) со статусом `draft`, связывается с `solution_plants`, если схема была построена на основе готового `landscape_solution`.

## 6. AI-описания

**Что делает.** Превращает сырую строку прайс-листа поставщика (как в вашем файле) в полноценную структурированную карточку товара: название по-русски и на латыни, привлекательное описание, характеристики в `plant_attribute_values`.

**Пайплайн (детально, потому что это первая точка контакта с реальными данными поставщика):**
1. **Парсинг (детерминированный код, не LLM):** регулярные выражения вычленяют из строки известные паттерны — объём контейнера (`Co\d+`, `\d+\s*л`), форму кроны (`ШТАМБ`), диапазон высоты (`\d+-\d+`), латынь в скобках. Это быстро и бесплатно там, где паттерн однозначен.
2. **LLM — только для неоднозначного остатка:** то, что не разобрал парсер (например, отличить «Со2» от опечатки, сопоставить русское название сорта с точной латинской номенклатурой, если латыни в строке нет), передаётся LLM с инструкцией **не придумывать** латинское название, если модель не уверена — в этом случае поле остаётся пустым и попадает в очередь ручной проверки поставщиком.
3. **Генерация описания:** отдельный вызов LLM пишет 2–3 предложения маркетингового описания на основе уже провалидированных структурированных данных (никогда — на основе сырой строки напрямую), в стиле, заданном Design System (Этап 3, раздел «Написание текста»).
4. Результат сохраняется в `translations` (entity_type='plant', field='description', locale='ru') и в `plant_attribute_values`; создаётся черновая карточка `plants` со статусом `draft` — публикует её поставщик после проверки, AI никогда не публикует напрямую.

**Пример на реальных данных — построчно:**

| Шаг | Значение |
|---|---|
| Сырая строка | `Бересклет Форчуна Эмеральд Гэити Co5Pa ШТАМБ 60-120 (Euonymus fortunei Emerald Gaiety)` |
| Парсер извлёк | контейнер: `Co5`, форма: `штамб (Pa)`, высота: `60–120 см`, латынь: `Euonymus fortunei 'Emerald Gaiety'` |
| LLM извлёк (неоднозначное) | сорт: `Emerald Gaiety` → тип листвы: `пёстролистный` (по справочнику известных сортов, с пометкой «сгенерировано AI, требует проверки поставщиком») |
| Сгенерированное описание | «Бересклет Форчуна «Эмеральд Гэити» на штамбе — компактный вечнозелёный кустарник с бело-зелёной пёстрой листвой, высота 60–120 см. Хорошо подходит для одиночных акцентных посадок и невысоких бордюров.» |
| Статус | `draft`, ожидает подтверждения поставщика перед публикацией |

**Риск и защита:** карточка с полями, сгенерированными AI, визуально помечена в кабинете поставщика бейджем «Заполнено AI — проверьте» (перекликается с UX Bible, раздел 5.2) до момента подтверждения человеком.

## 7. AI-проверка фотографий

**Что делает.** При загрузке фото товара проверяет: (а) соответствует ли изображение заявленному виду/сорту растения, (б) достаточно ли качество фото для публикации (резкость, освещение, отсутствие посторонних объектов/лиц), (в) не дублирует ли фото уже существующее в каталоге (защита от копирования чужих фото конкурентов).

**Пайплайн:**
1. Vision-модель классифицирует растение на фото и сравнивает с `latin_name`/`category_id` карточки — при явном несовпадении (например, к карточке «Туя западная Брабант» прикреплено фото можжевельника) карточка не публикуется автоматически, а уходит в очередь ручной проверки администратора (расширение `verification_documents`-логики из Этапа 5 на фото товаров).
2. Технические метрики качества (резкость, экспозиция) — простые CV-эвристики, не требуют LLM.
3. Перцептивный хэш (`pHash`) фото сравнивается с хэшами уже загруженных изображений в `plant_images` — обнаруживает повторное использование чужих фото.

**Пример на реальных данных.** В прайсе 32 позиции можжевельника и 21 позиция туи — визуально многие сорта близки, и это ровно та ситуация, где поставщик мог случайно перепутать файл при массовой загрузке (см. массовый импорт CSV, Этап 4, раздел 5.2). AI-проверка — это защита каталога от таких ошибок до того, как их увидит покупатель, а не после жалобы.

**Важно:** это проверка соответствия вида/качества фото, а не медицинская или биологическая экспертиза — AI не выносит вердикт о здоровье растения на фото, только о соответствии заявленному товару.

## 8. AI-переводы

**Что делает.** Переводит карточки товаров, категории, блог и FAQ на языки платформы (Этап 4, раздел 11), сохраняя ботаническую терминологию точной, а не буквальной.

**Пайплайн:**
1. Перевод происходит на уровне записи `translations` (Этап 5) — для каждой недостающей локали создаётся черновой перевод.
2. **Terminology-guard:** перед переводом LLM получает глоссарий устоявшихся ботанических и отраслевых терминов (например, «Со2» — единица объёма контейнера, не переводится и не интерпретируется как код; «штамб» → «standard form», а не дословно) — глоссарий хранится как отдельная таблица `translation_glossary(term, locale, approved_translation)` и пополняется вручную редактором по мере обнаружения ошибок.
3. Латинские названия **никогда не переводятся** — передаются как есть во все локали (это уже интернациональный стандарт, LLM явно инструктируется не трогать текст в `latin_name`).
4. Переводы вешают статус `machine` до подтверждения носителем языка (важно для стран запуска — Этап 1, раздел 5.1), после подтверждения — статус `verified`.

**Пример на реальных данных.** «Можжевельник скальный Блю Эрроу» → на английский переводится как «Rocky Mountain Juniper 'Blue Arrow'», а не дословно «Rocky juniper Blue Arrow» — только глоссарий и справочник культурных названий дают такую точность, обычный машинный перевод строки из прайса даст менее узнаваемый на рынке результат.

## 9. AI-помощник менеджеру

**Что делает.** Внутренний AI-ассистент для сотрудников платформы (администраторов, менеджеров по работе с поставщиками) — не путать с AI-помощником покупателя/поставщика из Этапа 2. Помогает обрабатывать очередь верификации, заявки и споры быстрее.

**Возможности:**
- Суммаризация новой заявки на верификацию поставщика (документы, история, риск-флаги) в 3 строки перед тем, как администратор откроет карточку целиком.
- Черновик ответа в споре (`disputes`, Этап 5) на основе переписки и приложенных доказательств — администратор редактирует и отправляет, а не пишет с нуля.
- Обнаружение аномалий в прайс-листах при массовой загрузке (Этап 4, раздел 5.2) — например, цена товара в 10 раз ниже средней по категории может быть опечаткой, AI подсвечивает такие строки менеджеру до публикации.
- Ежедневная сводка: «12 новых заявок на верификацию, 3 спора требуют решения сегодня (дедлайн SLA), средняя цена на можжевельники в каталоге выросла на 8% за неделю».

**Где в БД:** отдельная роль в `users.role = 'admin'`, читает `requests`, `disputes`, `plants`, `prices` с историей изменений (нужна таблица `price_history`, если понадобится трендовая аналитика — расширение к Этапу 5 при необходимости).

**Риск и защита:** ассистент менеджера **не принимает решения сам** (не подтверждает верификацию, не закрывает спор) — только готовит черновик и рекомендацию, финальное действие всегда за человеком, это зафиксировано как жёсткое архитектурное ограничение, а не просто рекомендация UX.

## 10. AI-рекомендации

**Что делает.** «Похожие товары», «часто покупают вместе», персональные рекомендации на дашборде покупателя (Этап 2, раздел 6.1).

**Пайплайн:**
1. **Похожие товары** — embedding-сходство по названию/атрибутам/категории (например, у «Можжевельник скальный Блю Эрроу» — 32 родственные позиции можжевельника в одном только вашем прайсе, есть из чего рекомендовать содержательно, а не случайно).
2. **Часто покупают вместе** — классический collaborative filtering по истории `order_items` (Этап 4), без LLM — это статистика, не генерация.
3. **Персональные рекомендации на дашборде** — LLM комбинирует историю закупок компании-покупателя + сезон + новые поступления у избранных поставщиков (`favorites`, Этап 5) в короткое естественно-языковое объяснение («Сезон посадки хвойных начинается — у 2 ваших поставщиков новое поступление туи»), а не просто список.

**Где в БД:** `plant_embeddings`, `order_items`, `favorites`, кэш пересчитанных рекомендаций — материализованное представление, обновляемое раз в сутки (не на каждый заход пользователя — дорого и не нужно для B2B-цикла закупки).

## 11. AI-генерация готовых решений

**Что делает.** Автоматически собирает записи в `landscape_solutions`/`solution_plants` (Этап 5) — готовые пакеты вроде «Живая изгородь эконом» или «Хвойный сад для тени» — на основе анализа каталога, а не вручную сотрудником с нуля.

**Пайплайн:**
1. AI кластеризует каталог по функциональному назначению (используя `attributes` — тип использования, требования к свету/влаге) и находит группы товаров, которые типично комбинируются в проектах (по данным реальных `projects`/`project_solutions`, если они уже есть, либо по ботанической логике на старте).
2. Для каждого кластера LLM формирует название решения, описание, типовой состав (`solution_plants` с `qty_per_unit`) и ценовой диапазон (`price_from` — вычисляется детерминированно из `prices`, не выдумывается моделью).
3. Черновик решения уходит на модерацию контент-менеджеру (аналогично AI-описаниям, раздел 6) перед публикацией на сайте.

**Пример на реальных данных.** Кластер «низкий бордюр, солнце, компактные кустарники» из вашего прайса естественно соберёт «Барбарис Тунберга Багатель» (1000 ₽), «Барбарис Тунберга Голден Ринг» (950 ₽), «Пузыреплодник калинолистный Диаболо» (900 ₽) — AI предложит готовое решение «Контрастный низкий бордюр» с расчётной ценой за погонный метр, что реально ускоряет выход на рынок B2C2-слоя (Этап 1, цель Б5), потому что не нужно вручную придумывать 20+ пакетных предложений с нуля.

## 12. AI-калькуляторы

**Что делает.** Расширяет три калькулятора из Этапа 2 (раздел 9) там, где чистая формула недостаточна — интерпретация неструктурированного ввода на входе калькулятора.

| Калькулятор | Где AI, а где формула |
|---|---|
| Объём для проекта | **Формула** считает количество растений по площади/периметру и плотности — это чистая математика, без LLM. **AI** нужен только на входе: превратить «участок примерно 6 соток, забор буквой Г» в структурированные метры периметра, либо распознать простой план участка по загрученному фото/скетчу (vision-модель извлекает контур и примерный масштаб). |
| Доставка | Полностью детерминированный расчёт (Этап 4) — AI не участвует, кроме объяснения результата человеческим языком в AI-помощнике (Этап 2, раздел 10.1: «Где мой заказ №1234?»). |
| Экономия при опте | **Формула** сравнивает цену по ступеням из `prices`. **AI** используется только при генерации рекомендации в диалоге («если возьмёте на 15 штук больше — цена за единицу упадёт на 12%») как естественноязыковая обёртка над уже посчитанным числом, а не как источник самого числа. |

**Архитектурное правило (повтор принципа из раздела 2.2):** ни один калькулятор не должен зависеть от LLM для получения итоговой цифры — LLM только помогает собрать входные данные из неструктурированного запроса и объяснить результат.

## 13. Сквозные принципы: промпты, кэш, стоимость, безопасность

### 13.1 Промпт-инжиниринг

- Каждая из 10 фич — отдельный системный промпт с фиксированной ролью, а не один универсальный промпт-«на всё» — так проще тестировать и версионировать независимо.
- Системные промпты хранятся в `supabase/functions/ai-orchestrator/prompts/*.md`, версионируются вместе с кодом (не в БД) — изменение промпта проходит тот же CI/CD, что и код (Этап 4, раздел 16).
- Structured output (JSON-схема) обязателен там, где ответ идёт в БД (описания, атрибуты, переводы) — свободный текст допустим только в диалоговом AI-помощнике.

### 13.2 Кэширование

Таблица `ai_cache` (Этап 5) используется для: одинаковых вопросов в AI-поиске/помощнике, повторяющихся паттернов парсинга описаний (например, «Co5 Pa ШТАМБ» будет встречаться в каталоге сотни раз у разных поставщиков — разобранный паттерн переиспользуется, а не пересчитывается каждый раз). TTL кэша короче там, где ответ зависит от остатков/цен, и длиннее там, где не зависит (перевод латинского названия не устаревает).

### 13.3 Стоимость и лимиты

- Дешёвые детерминированные шаги (парсинг регулярками, расчёт калькуляторов, collaborative filtering) выполняются в первую очередь — LLM вызывается только на то, что действительно требует понимания языка/изображения.
- Rate limiting на AI-эндпоинты по компании (Этап 4, раздел 12.3) — отдельные квоты для дешёвых фич (перевод, поиск) и дорогих (vision-проверка фото, AI-дизайнер).
- Массовая генерация описаний (например, разовая обработка всего прайса нового поставщика) — выполняется асинхронно фоновой задачей, а не синхронно при загрузке файла, чтобы не блокировать UI и не упираться в лимиты API за секунды.

### 13.4 Безопасность и качество

- **Ничего медицинского/фитосанитарного не утверждается без источника.** Если поле (токсичность, морозостойкость, инвазивность вида в конкретном регионе) не заполнено человеком или не взято из проверенного справочника — AI явно пишет «уточняется», а не оценивает по вероятности.
- **Человек подтверждает публикацию.** AI-описания, AI-переводы, AI-сгенерированные решения — всегда в статусе `draft`/`machine` до подтверждения ответственным человеком (поставщиком, контент-менеджером).
- **Логирование для аудита.** Каждый вызов AI-оркестратора логируется с `feature`, `role`, `input_hash`, `model_version` — при обнаружении систематической ошибки (например, неверный парсинг определённого формата контейнера) можно найти все затронутые карточки одним запросом.
