## 1. Структура URL

### 1.1 Домен и локали

**Рекомендация: одна доменная зона + подпапки локалей**, а не ccTLD (`.de`, `.pl`) на старте — это консолидирует ссылочный вес и авторитет домена в одном месте, что критично для нового сайта без наработанной истории (PRD, Этап 1 — платформа стартует с нуля против устоявшихся Dehner/Jardiland/OBI):

```
tamga.green/en/...     — английский (лингва франка B2B, Этап 4 раздел 11)
tamga.green/de/...     — немецкий
tamga.green/pl/...     — польский
tamga.green/nl/...     — нидерландский
```

Переход на ccTLD или поддомены по странам — пересматривается после Б4 из PRD (масштабирование на 3–5 стран), когда объём органического трафика на страну оправдает раздельную стратегию.

### 1.2 Паттерны URL по типам страниц

| Тип страницы | Паттерн | Пример |
|---|---|---|
| Категория каталога | `/{locale}/catalog/{category-slug}/` | `/en/catalog/conifers/thuja/` |
| Товар | `/{locale}/catalog/{category-slug}/{product-slug}/` | `/en/catalog/conifers/thuja/thuja-occidentalis-smaragd/` |
| Профиль поставщика | `/{locale}/suppliers/{company-slug}/` | `/en/suppliers/kwekerij-van-doorn/` |
| Готовое решение | `/{locale}/solutions/{solution-slug}/` | `/en/solutions/evergreen-hedge-budget/` |
| Проект/кейс | `/{locale}/projects/{project-slug}/` | `/en/projects/private-garden-warsaw-120sqm/` |
| Блог | `/{locale}/blog/{post-slug}/` | `/en/blog/thuja-winter-care-guide/` |
| FAQ | `/{locale}/faq/` (+ якоря по категориям вопросов) | `/en/faq/#shipping` |

### 1.3 Принципы формирования slug

- **Товар: категория в пути + slug из названия+сорта, без ID.** `thuja-occidentalis-smaragd`, а не `product-84f2a1`. Латинское название в slug (Этап 5, поле `latin_name`) улучшает соответствие ботаническим запросам на любом языке, даже когда локализованное название ещё не переведено (Этап 4, раздел 11 — fallback на английский).
- **Slug независим от `id`, но стабилен.** При смене названия/категории `slug` не меняется автоматически — иначе теряются накопленные обратные ссылки и позиции в выдаче; редиректы 301 настраиваются вручную при осознанном ребрендинге позиции.
- **Никаких query-параметров в канонических URL товаров/категорий** — фильтры и сортировка передаются через `?` (раздел 5.2), а не превращаются в отдельные индексируемые пути.

## 2. Schema.org

Структурированные данные — на каждом типе страницы, в формате JSON-LD (не микроразметка в HTML-атрибутах — проще поддерживать и тестировать отдельно от вёрстки).

| Страница | Схема | Ключевые поля |
|---|---|---|
| Главная | `WebSite` + `SearchAction` | Даёт Google возможность показать сайтлинк-поиск прямо в выдаче |
| Категория | `CollectionPage` + `BreadcrumbList` + `ItemList` (первые 20 товаров) | `ItemList` помогает показать карусель товаров в расширенных сниппетах |
| Товар | `Product` + `Offer` + `AggregateRating` + `BreadcrumbList` | См. пример в Этапе 4, раздел 15.2 — здесь дополнительно `availability` синхронизируется с `availability.quantity` (Этап 5) в реальном времени при каждой ISR-ревалидации |
| Профиль поставщика | `Organization` + `AggregateRating` + `sameAs` (ссылки на внешние профили компании, если есть) | Повышает доверие в сниппете, работает на бренд поставщика внутри платформы |
| Готовое решение | `Product` (как «пакетное предложение») или `Service`, в зависимости от того, что ближе к юридической природе оффера | Обсудить с юристом на этапе финализации — разница влияет на тип разметки |
| Проект/кейс | `CreativeWork` + `ImageObject` (галерея) | |
| Блог | `Article` + `BreadcrumbList` | `datePublished`/`dateModified` обязательны — влияют на свежесть в выдаче |
| FAQ | `FAQPage` | Прямой путь к расширенному сниппету с вопросами прямо в выдаче — самая быстрая win-win разметка для B2B-запросов вида «нужен ли фитосертификат для перевозки растений между странами ЕС» |

**Валидация:** каждая разметка проходит через Google Rich Results Test и Schema.org Validator в CI перед деплоем (не полагаемся только на визуальную проверку) — простой Playwright-тест, читающий JSON-LD со страницы и сверяющий обязательные поля.

## 3. Open Graph и социальные превью

### 3.1 Базовый набор тегов (на каждой публичной странице)

```html
<meta property="og:type" content="product" />
<meta property="og:title" content="Thuja occidentalis 'Smaragd' — Tamga Green" />
<meta property="og:description" content="Морозостойкая туя для живой изгороди, зона 5. От 4,20 € — заказ у 6 верифицированных поставщиков." />
<meta property="og:image" content="https://tamga.green/og/plants/thuja-occidentalis-smaragd.png" />
<meta property="og:url" content="https://tamga.green/en/catalog/conifers/thuja/thuja-occidentalis-smaragd/" />
<meta name="twitter:card" content="summary_large_image" />
```

### 3.2 Динамическая генерация OG-изображений

Вместо статичной og:image (первое фото товара часто плохо читается в ленте соцсетей без контекста) — **генерируемое на лету OG-изображение** через Vercel OG / Satori: фото товара + название + цена + бейдж поставщика, собранные в единый брендированный шаблон по токенам Design System (Этап 3). Технически — Route Handler `GET /api/og/[type]/[slug]`, рендерящий SVG→PNG на edge, с кэшированием по CDN (не пересчитывается на каждый шеринг).

### 3.3 Зачем это конкретно для B2B-маркетплейса

Закупщик садового центра часто пересылает ссылку на товар коллеге в Slack/WhatsApp/email для согласования — качественное превью с ценой и наличием прямо в превью-карточке messenger'а увеличивает клик-through без дополнительных действий пользователя.

## 4. Карты сайта (Sitemaps)

### 4.1 Архитектура

```
/sitemap.xml                          — sitemap-индекс
  ├── /sitemaps/static-{locale}.xml   — статичные страницы (главная, о нас, FAQ...)
  ├── /sitemaps/categories-{locale}.xml
  ├── /sitemaps/products-{locale}-{n}.xml   — чанки по 50 000 URL (лимит Google)
  ├── /sitemaps/suppliers-{locale}.xml
  ├── /sitemaps/solutions-{locale}.xml
  ├── /sitemaps/projects-{locale}.xml
  └── /sitemaps/blog-{locale}.xml
```

Отдельный sitemap-индекс на каждую локаль (Этап 4, раздел 15.4) — упрощает диагностику, если у конкретного языка проблема с индексацией.

### 4.2 Генерация и обновление

- Sitemap продуктов генерируется Route Handler'ом (Этап 4, раздел 8) динамически из `plants where status = 'active'`, кэшируется на 1 час.
- При публикации/архивации товара — sitemap не пересобирается синхронно (дорого при частых изменениях остатков), достаточно часового кэша; для срочных случаев (крупный новый поставщик разом опубликовал каталог) — ручной триггер пересборки + **IndexNow API ping** (Bing/Yandex) и **Google Search Console Sitemaps API** для ускоренной переиндексации.
- **Image sitemap extension** — для каждого товара включаем до 5 изображений (`plant_images`) прямо в sitemap товаров через `<image:image>` — заметно ускоряет попадание фото растений в Google Images, что для визуальной категории (сад/растения) даёт значимый дополнительный трафик.

## 5. Индексация и crawl budget

### 5.1 robots.txt

```
User-agent: *
Disallow: /*/dashboard/
Disallow: /*/cart/
Disallow: /*/checkout/
Disallow: /*/login/
Disallow: /*/onboarding/
Disallow: /*/admin/
Disallow: /api/
Allow: /

Sitemap: https://tamga.green/sitemap.xml
```

### 5.2 Проблема фасетных фильтров (главный SEO-риск маркетплейса)

Каталог с фильтрами (Этап 7, раздел 4) технически может сгенерировать десятки тысяч комбинаций URL (`?category=conifers&zone=5&price=100-500&supplier=...`) — если это всё индексируется, crawl budget уходит на дубли вместо реальных страниц. Решение:

| Ситуация | Обработка |
|---|---|
| Товары/категории без фильтров | Индексируется, канонический URL |
| Категория + 1 значимый фильтр, дающий самостоятельный смысл поискового запроса (например, «туи по зоне морозостойкости 5») | Индексируется как отдельный **предсобранный лендинг** (не динамический query-параметр, а нормальный путь `/catalog/conifers/thuja/zone-5/`) — таких комбинаций ограниченное, курируемое количество, а не автогенерация всех сочетаний |
| Любая комбинация из 2+ фильтров через query-параметры | `<meta name="robots" content="noindex,follow">` + `rel=canonical` на базовую страницу категории — краулится (follow), чтобы находить сами товары, но не индексируется как отдельная страница |
| Пагинация (страница 2, 3…) | Каждая страница — самостоятельный `canonical` на саму себя (не на страницу 1 — распространённая ошибка, из-за которой Google не видит товары глубже первой страницы), `noindex` не ставится |

### 5.3 Товары «нет в наличии»

Как зафиксировано в Этапе 7 — карточка не снимается с индексации при нулевом остатке (только меняется статус в `Product.offers.availability` на `OutOfStock`, раздел 2). Полное удаление/redirect по товару, который вернётся в продажу через 2 недели, обнулило бы накопленные позиции в выдаче без необходимости.

### 5.4 Мультиязычные дубли

`hreflang` (Этап 4, раздел 15.4) устраняет риск, что Google посчитает `/en/...` и `/de/...` дублями — каждая версия явно объявляет себя альтернативой остальных, включая `x-default`.

## 6. Метатеги

### 6.1 Шаблоны Title/Description по типам страниц

| Тип страницы | Title | Description |
|---|---|---|
| Товар | `{Название} — купить от {цена от} € \| Tamga Green` | `{Название}, зона морозостойкости {N}. В наличии у {K} поставщиков в {страна}. Заказ от {min_qty} шт с доставкой по Европе.` |
| Категория | `{Название категории}: {N} товаров от проверенных питомников \| Tamga Green` | `Каталог {категория} — сравните цену и наличие у {N} верифицированных поставщиков Европы. Оптовые цены, доставка растений.` |
| Профиль поставщика | `{Компания} — {страна}, {N} категорий товара \| Tamga Green` | `{Компания}: {краткое описание}. {N} товаров в каталоге, рейтинг {X}★.` |
| Блог | `{Заголовок статьи} \| Tamga Green Блог` | Первые ~155 символов тела статьи, без обрезания посреди слова |

Все шаблоны реализуются через `generateMetadata` (Этап 4, раздел 15.1) как функции над данными из БД — не ручной ввод для каждой из тысяч карточек, а формула, которую поставщик может точечно переопределить полями `meta_title`/`meta_description` (опциональное расширение таблицы `plants`/`translations`) для топовых по трафику позиций.

### 6.2 Пример конкретного тайтла на реальных данных

Для позиции из вашего прайса «Бересклет Форчуна Эмеральд Гэити Co5Pa ШТАМБ 60-120»:
`Euonymus fortunei 'Emerald Gaiety' на штамбе — купить от 23 € | Tamga Green` — латынь и сорт в title заметно повышают релевантность для запросов и от профессиональных ландшафтников (ищут по латыни), и от частных покупателей (ищут по разговорному названию, которое AI-описание, Этап 6, добавит в основной текст карточки).

## 7. Скорость и Core Web Vitals

### 7.1 Целевые пороги (публичные страницы — приоритет №1 для SEO)

| Метрика | Цель | Почему |
|---|---|---|
| LCP (Largest Contentful Paint) | ≤ 2,5 сек | Прямой ранжирующий фактор Google с 2021 года |
| INP (Interaction to Next Paint) | ≤ 200 мс | Заменил FID, критичен для интерактивных фильтров каталога |
| CLS (Cumulative Layout Shift) | ≤ 0,1 | Критично для страниц с изображениями товаров, загружающимися асинхронно |

### 7.2 Конкретные технические меры (дополняют Этап 4, раздел 13)

- **LCP на карточке товара** — главное фото товара грузится с `priority` (Next.js Image), без lazy loading, в формате AVIF/WebP с явными `width`/`height` — устраняет и медленный LCP, и CLS одновременно.
- **Шрифты без сдвига макета** — `next/font` с `font-display: swap` и точным резервированием места под текст (`size-adjust`) для Fraunces/Inter (Этап 3) — иначе смена шрифта после загрузки сдвигает контент.
- **INP на странице каталога с фильтрами** — тяжёлая перерисовка сетки товаров при смене фильтра выполняется через `useTransition` (React 19, Этап 4 раздел 4), чтобы ввод в фильтр не блокировался пересчётом списка.
- **Skeleton вместо resize** — все асинхронные блоки (отзывы, рекомендации, блок «похожие товары») резервируют фиксированную высоту через skeleton (Этап 2, раздел 2.3) до подгрузки данных — ноль CLS от отложенного контента.
- **Мониторинг по реальным пользователям (RUM)**, не только в лаборатории — Vercel Speed Insights (Этап 4) сегментированный по locale/устройству, потому что мобильный CWV в регионах со слабым покрытием сети (Восточная Европа, PRD Этап 1) может систематически отличаться от desktop в Германии.

### 7.3 Google Search Console как источник правды

Отчёт «Основные интернет-показатели» в GSC — еженедельная проверка, потому что он агрегирует реальные полевые данные (CrUX) по URL-группам, а не по синтетическим тестам — расхождение между лабораторными измерениями и реальным полем на медленных мобильных сетях типично для контентных маркетплейсов.

## 8. Контентная стратегия

### 8.1 Модель «столб — кластер» (pillar-cluster) на реальном ассортименте

Категории из вашего прайса (Этап 6) напрямую подсказывают контентные столбы — это не абстрактный список ключевых слов, а прямое отражение того, что уже есть в каталоге:

```
Столб: "Хвойные растения для живой изгороди" (/blog/conifer-hedge-guide/)
 ├── Кластер: "Туя Смарагд: уход, посадка, обрезка"
 ├── Кластер: "Можжевельник скальный Блю Эрроу — для чего подходит"
 ├── Кластер: "Сколько саженцев туи нужно на погонный метр" → ссылка на калькулятор (Этап 2/6)
 └── Кластер: "Хвойные vs лиственные для изгороди: что выбрать"

Столб: "Кустарники с цветной листвой" (/blog/colorful-foliage-shrubs/)
 ├── Кластер: "Барбарис Тунберга: сорта и отличия" (в прайсе 12 сортов — готовый угол для сравнительной статьи)
 ├── Кластер: "Пузыреплодник Диаболо в ландшафтном дизайне"
 └── Кластер: "Бересклет Форчуна: штамбовая форма или кустовая"
```

Каждый кластер заканчивается перелинковкой на релевантные карточки товара и готовые решения (Этап 7) — трафик от информационного запроса конвертируется в переход в каталог, а не утекает после прочтения статьи.

### 8.2 Транзакционный vs информационный интент

| Тип запроса | Пример | Куда ведём |
|---|---|---|
| Транзакционный | «купить тую смарагд оптом» | Прямо на карточку товара/категорию |
| Информационный | «когда сажать тую осенью или весной» | На статью блога, с CTA в каталог |
| Смешанный (частый в B2B) | «поставщики хвойных растений Польша» | На фильтр каталога по региону/категории или на лендинг «Поставщики в Польше» |

### 8.3 Сезонность как контентная возможность, а не только риск

PRD (Этап 1, раздел 2.2) отметил сезонность как структурный риск бизнеса — контент-стратегия может частично сглаживать это: публикация «подготовка живой изгороди к зиме» в конце лета и «выбор растений на весну» зимой поддерживает органический трафик в низкий сезон продаж, готовя спрос к следующему пику вместо простоя блога.

### 8.4 Локальный SEO по странам роста

PRD (Этап 1, раздел 2.2) выделил Польшу, Румынию, Венгрию как недооценённые растущие рынки — контент-план явно включает локализованные (не просто переведённые) статьи под эти рынки: региональные особенности климата, местные нормы озеленения, локальные кейсы (`projects`, Этап 5) — это одновременно SEO-сигнал релевантности локали и содержательная ценность для локального покупателя.

### 8.5 FAQ как источник featured snippets

Вопросы в `faq_items` (Этап 5) формулируются напрямую как реальные поисковые запросы («нужен ли фитосанитарный сертификат для перевозки растений между странами ЕС», «как оплатить заказ с отсрочкой платежа») — с `FAQPage`-разметкой (раздел 2) это один из самых быстрых путей к расширенному сниппету для B2B-тематики, где конкуренция по классическим коммерческим запросам выше.

### 8.6 Отзывы как источник свежести контента

Отзывы поставщиков (`reviews`, Этап 4) на публичной странице товара/поставщика — не только доверие для покупателя, но и постоянно обновляемый пользовательский контент на странице, что положительно влияет на сигналы свежести без ручной работы контент-команды.

## 9. Международное SEO

- **hreflang** на каждой странице, включающий все локали + `x-default` (Этап 4, раздел 15.4) — реализуется автоматически по `next-intl` middleware, не вручную по странице.
- **Валюта и локальные форматы** — отображаются по locale, но не создают отдельных индексируемых URL (валюта — не SEO-сущность, а UX-слой поверх той же страницы).
- **Локализованные slug категорий**, где это естественно для языка (`/de/katalog/nadelgehoelze/` вместо дословного транслита) — обсуждается с носителями языка на этапе вычитки (Этап 4, раздел 11), но `latin_name` в товарных slug остаётся языконезависимым.
- **Google Merchant Center / товарный фид** — не входит в MVP, но архитектурно закладывается: структура `Product`+`Offer` (раздел 2) уже совместима с форматом фида Google Shopping, что становится дополнительным каналом трафика на Фазе 2 без переделки схемы данных.
