### Отчёт Phase 1

**Ограничение среды.** В этой облачной сессии нет Docker-демона — `supabase start`
не может быть запущен здесь физически. Вместо этого миграции провалидированы
против нативного Postgres 16 (пакет уже стоял в системе) с временной stub-схемой
`auth.users`/`auth.uid()`/`auth.role()` — это подтверждает корректность SQL и RLS-
логики, но не проверяет реальные Supabase Auth/Storage/Realtime. Зафиксировано в
README.md — пользователю нужно прогнать `supabase start` на своей машине с Docker
как первый шаг (см. README, "Что нужно установить").

**RLS smoke-test (не просто "политика создана", а реально сработала).** Создал
роль `authenticated` (без bypass RLS, как у настоящей Supabase-роли) и двух тестовых
поставщиков; User B не смог ни увидеть, ни обновить черновой товар User A
(`update ... where slug='plant-a-draft'` от лица B вернул `UPDATE 0`). Полноценный
тест на реальных HTTP-запросах с JWT — по плану Phase 2.

**[решено самостоятельно] — находки/адаптации в процессе Phase 1:**

- **`translations` не мёржится через PostgREST embedding.** Унаследованный код
  каталога (`getPlantsByCategory`/`getCategories`) пытался делать
  `.from("plants").select("... translations!inner(...)")` — но `translations`
  полиморфна и **сознательно без FK** на `plants` (Database Design §1, принцип 4).
  PostgREST embedding требует реального FK, значит это никогда не заработало бы
  в реальном Supabase, не только в типах. Переписал на два отдельных запроса
  (plants+реальные FK-embeds, затем translations по `entity_id in (...)`) с мёржем
  в коде и откатом на `en`, если для локали нет перевода (Architecture §11).
- **`search_vector` нельзя поддерживать так, как описано в Architecture §9.1.**
  Тот пример триггера читает `new.name->>'en'` — но Database Design §8 вынес
  name/description в `translations`, так что на INSERT/UPDATE строки `plants`
  перевода ещё не существует. Реализовал через пару триггеров: один на `plants`
  (пересчёт при смене `latin_name`), другой на `translations` (пересчёт при
  добавлении/изменении `name`/`description` для `entity_type='plant'`).
- **Fraunces не имеет кириллических глифов** (Google Fonts отдаёт только
  latin/latin-ext/vietnamese) — заголовки на `ru` будут рендериться системным
  serif-фолбэком вместо Fraunces. Это ограничение самого шрифта, а не конфигурации;
  альтернативного дисплей-шрифта с кириллицей документы не называют, менять токен
  не стал — просто зафиксировал ограничение.
- **Версии пакетов сдвинуты вперёд, как и предупреждала прошлая офлайн-сессия:**
  `lucide-react` 0.383→^1.24 (0.383 не поддерживает React 19 в peerDependencies),
  `@supabase/ssr` 0.5→^0.12 (0.5 давал несовместимые типы генериков с
  `@supabase/supabase-js` 2.110, из-за чего вся типизация запросов схлопывалась
  в `never`).
- **`lib/supabase/types.ts` требует `Relationships`/`Views`/`Functions`/`Enums`/
  `CompositeTypes`**, а не только `Row`/`Insert`/`Update` — без них дженерики
  `@supabase/supabase-js` не резолвятся. Добавил корректные `Relationships` для
  реальных FK (`plant_images`/`prices`/`availability` → `plants`).
- **ESLint 9 flat config не существовал** (`next lint` спрашивал интерактивный
  выбор) — создал `eslint.config.mjs` с `next/core-web-vitals` + `next/typescript`
  напрямую, без диалога.
- **`@tailwindcss/typography`** добавлен в `tailwind.config.ts` plugins и
  `package.json` — Architecture §5 перечисляет оба плагина, в унаследованном
  каркасе был только `forms`.
- **`i18n.ts` → `i18n/request.ts`** — Next.js 15/next-intl помечают путь `./i18n.ts`
  как deprecated, поправил путь и относительный импорт `messages/`.

### Отчёт Phase 2

**Находка: коллизия route groups в System Architecture §2.** Дерево проекта в
документе рисует `(supplier)/dashboard/page.tsx` и `(buyer)/dashboard/page.tsx` —
но круглые скобки в Next.js App Router создают route group, который **не добавляет
сегмент в URL**, то есть оба физически компилировались бы в один и тот же путь
`/dashboard` и Next.js отказался бы собираться. [решено самостоятельно]: использованы
настоящие сегменты-папки `app/[locale]/supplier/dashboard` и `app/[locale]/buyer/dashboard`
(не группы) — они же стали префиксами для role-gating в middleware.

**Находка при собственной ревизии RLS (см. `0007_verification_gating.sql`).**
Сверяя написанные в Phase 1 политики с тем, что реально требует UX Bible §4.3
("пока не подтверждено... недоступны заказ/загрузка товаров"), обнаружил, что:
1. `public_read_active_plants` (0001) не проверяла `companies.verification_status`,
   в отличие от точного примера в Architecture §7.4 — исправлено, протестировано
   (см. ниже: "фейковый" active-товар pending-компании невидим анониму).
2. Ни одна write-политика не блокировала действия pending-аккаунтов — добавлены
   проверки `verification_status='approved'` в политики публикации товара и
   создания заказа. Это стояло бы "тихой миной" до Phase 4/5, когда чекаут/CMS
   реально заработали бы без такой проверки.

**RLS smoke-тесты этой фазы (реальные SQL-запросы, не только "политика создана»):**
- Pending-поставщик → `insert into plants (...)` → `ERROR: new row violates RLS`.
- Pending-покупатель → `insert into orders (...)` → `ERROR: new row violates RLS`.
- Анонимная роль видит 165 реальных active-товаров approved-поставщика, но 0 для
  "фейкового" active-товара pending-компании (добавлен напрямую в обход RLS, чтобы
  проверить именно SELECT-политику, а не полагаться на то, что pending не может
  дойти до active).
- Хук `custom_access_token_hook(event)` на реальном вызове корректно добавил
  `{"role": "supplier", "company_id": "..."}` в claims.
- Storage: владелец компании читает/пишет свою папку в `verification-docs`,
  посторонний пользователь не может ни прочитать чужую, ни записать в неё
  (`ERROR: new row violates RLS` при попытке "подбросить" файл в чужую папку).

**[решено самостоятельно] — прочие находки:**
- UX Bible §4.2 не называет отдельное поле "имя контактного лица", хотя
  `users.full_name` `NOT NULL` — добавлено обязательное поле `contactName` в обе формы.
- Платформенная очередь верификации администратора (UX Bible §12.1) не назначена
  явно ни одной фазе Build Prompt (`Tamga_Green_Admin_Panel.md` — это CMS
  поставщика, не кабинет платформенного админа) — собрана в минимальном виде
  (`/admin/verification`, подтвердить/отклонить с причиной) ровно настолько, чтобы
  протестировать сквозной флоу онбординга; полноценный просмотр документов
  (PDF-вьюер и т.п.) — бэклог, не блокирует MVP.
- **Локализация текста экранов регистрации/логина/статуса — на русском хардкодом**,
  не через `next-intl`/`messages/*.json`. Это реальный технический долг: пользователь
  с `locale=en` увидит русский текст на этих экранах. Осознанно отложено (объём
  правок был бы велик для этой фазы), зафиксировано здесь как задача — см. "Осталось"
  ниже. Каталожные страницы (Phase 1/3) эту проблему не имеют, т.к. контент оттуда
  идёт из БД (`translations`), а не из статических UI-строк.
- `npm run build`/`typecheck`/`lint` — реально прогнаны после каждого значимого
  изменения в этой сессии (не просто "должно собраться").

### Отчёт

**Ограничение схемы, из-за которого пришлось принять решение.** `attributes.
category_id` — одиночный nullable FK (одна категория или `null` = глобально),
а `attributes.code` уникален (`unique not null`) — то есть у одного и того же
логического атрибута не может быть несколько строк под разные категории.
Схема физически не может выразить "атрибут применим к 3 из 4 категорий, но не
к 4-й" — только "везде" или "ровно в одной". Rule 2 запрещает переделывать
схему, поэтому работал в рамках этого ограничения, а не обходил его лишними
таблицами.

**[решено самостоятельно] Распределение 6 атрибутов.** Поднял живую Postgres-
БД с полным сидом (165 реальных позиций) и посчитал, где атрибуты реально
заполнены/различаются, вместо того чтобы гадать:
- `hardiness_zone`, `light`, `height_range`, `container_volume` — остались
  глобальными (`category_id = null`): зимостойкость и освещение значимы для
  любого растения в каталоге, а `container_volume`/`height_range` уже реально
  встречаются во всех 4 верхних категориях (проверено запросом).
- `foliage_type` (вечнозелёное/листопадное/пёстролистное) — привязан к

## Backlog: откат массового изменения цен ✅ (сделано, отчёт ниже)

Admin Panel §4.2: "действие логируется... с возможностью отменить одним
кликом в течение 24 часов («откат» хранит предыдущие значения `prices` во
временной таблице `price_change_log`)". Данные писались с самого Phase 5,
кнопки отмены не было.

### Отчёт

**Область ограничена ценами, не остатками — намеренно.** Спецификация
описывает откат только для цен (`price_change_log`); для массового изменения
остатков в схеме нет аналогичного лог-механизма (никакой `stock_change_log`),
и придумывать новую таблицу для этого значило бы нарушить rule 2. Массовое
изменение остатков как было без отката, так и осталось — явно
задокументировано в коде и здесь, а не тихо забыто.

**Реализация (`lib/actions/bulkUpdate.ts`):**
- `getRecentPriceRollbacks()` — список `bulk_price_update` записей
  `audit_log` за последние 24 часа с количеством товаров, которые реально
  можно откатить (считается по фактическим строкам `price_change_log`, а не
  по значению `affected` из JSON — если строк лога почему-то не осталось,
  пункт не покажется).
- `rollbackBulkPriceUpdate(auditLogId, locale)` — проверяет окно 24ч по
  `audit_log.created_at`, восстанавливает `prices.price`/`currency` по
  сохранённым `previous_price`/`previous_min_qty`/`previous_currency` для
  каждой позиции, пишет отдельную запись `audit_log` с действием
  `bulk_price_update_rollback` (сам откат тоже входит в журнал действий —
  §9 требует полный аудит, не только прямые изменения).
- Строки `price_change_log` после отката НЕ удаляются (это потребовало бы
  policy на DELETE для владельца, которой в 0004-миграции нет — не стал
  добавлять RLS-политику сверх того, что уже определено в Database Design;
  повторный клик просто применит те же previous-значения ещё раз, без
  побочных эффектов).

**[решено самостоятельно] Откат виден только тому же аккаунту, что делал
изменение, не всей компании.** Унаследовано из RLS-политики `audit_log`
(`self_read_audit_log`: `actor_id = auth.uid()`, а не company-scoped) —
если у поставщика несколько сотрудников с доступом (Admin Panel §9, само
по себе backlog, "не обязательно для MVP"), коллега не увидит в списке
чужой bulk-update. Не менял эту RLS-политику ради этой фичи — исправление
такого масштаба вне объёма "добавить кнопку отката".

**Проверено вживую (не только билдом).** Поднял чистую Postgres-БД со всеми
9 миграциями, засеял двух реальных поставщиков (не тестовые заглушки в
смысле формы, а полноценные компании с ценами), симулировал ровно ту
последовательность SQL-запросов, что выполняет server action, через
`SET ROLE authenticated; SET app.current_user_id = ...`:
1. Владелец (актор bulk-update) видит только запись младше 24ч, старая
   (25ч) корректно не попадает в выборку.
2. Другой поставщик получает 0 строк и из `audit_log`, и из
   `price_change_log` — RLS блокирует чтение чужого лога отката.
3. Другой поставщик, пытаясь напрямую откатить цену через `UPDATE prices`,
   затрагивает 0 строк — цена (550) не меняется.
4. Владелец успешно откатывает свою цену обратно на 500.

Все 4 сценария отработали правильно. `npm run build`/`typecheck`/`lint` —
чистые. Живым `next dev` подтверждено, что `/supplier/products/bulk` и
`/supplier/products/new` не падают (307 → `/login` для анонима, как и
должно быть) — саму кнопку "Откатить" в интерфейсе визуально не нажимал,
поскольку это требует реальной авторизованной сессии поставщика, которой в
этой песочнице без Docker/живого Supabase нет (то же ограничение, что и в
предыдущих фазах); логика подтверждена прямым SQL против живой БД с
реальными данными, а не только тем, что страница отвечает 200/307.
